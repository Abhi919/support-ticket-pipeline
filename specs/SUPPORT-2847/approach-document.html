Development approach — SUPPORT-2847

Stakeholder summary · 2026-09-13 · Status: approved

Executive summary

We will deliver a small support ticket platform: a Spring Boot API backed by a persistent database and a React web UI. Tickets move through a fixed lifecycle (open → in progress → resolved → closed, with cancellation paths). The backend rejects invalid status jumps so teams cannot accidentally reopen closed work.

Problem & goals

Internal teams need a single place to log issues, assign owners, discuss via comments, and close work through a clear workflow. Data must survive restarts; the API must validate input and enforce lifecycle rules.

Proposed approach

  1. Write full specification (requirements, API contract, state machine) before any code.
  2. Implement the API in small tasks (entities → state machine → endpoints → tests).
  3. Build the React UI against the contract with meaningful error display.
  4. Verify each functionality flow in code before writing formal test cases.

Key functionality flows

FUN-001 — Create ticket

User submits the create form → API stores a new ticket with status Open → ticket appears in the list.

FUN-002 — List & search

User opens the home page → API returns tickets, optionally filtered by keyword and status → table updates.

FUN-003 — View & edit ticket

User opens a ticket → loads details → saves field changes → API persists updates.

FUN-004 — Change assignee

User updates assignee on the detail form → same save action updates ownership.

FUN-005 — Add comment

User posts a comment → API appends to the ticket thread → detail view refreshes.

FUN-006 — Status transition

User picks an allowed next step → API validates via state machine → status updates.

FUN-007 — Reject bad transition

Illegal move (e.g. closed → open) → API returns conflict → UI shows error banner.

FUN-008 — Validation errors

Invalid input → API returns field errors → UI surfaces readable messages.

Risks & mitigations

  • Lifecycle bypass — dedicated status endpoint + state machine tests.
  • Data loss — file-based H2, not in-memory only.

Out of scope

  • Login and role-based access
  • Email notifications
  • File attachments
